# 分支与版本维护规范

每次合并和发布都需要用户明确授权。验收通过不自动构成后续版本的合并或发布授权，也不自动新增发布流程。

## 三条分支的职责

| 分支 | 职责 | 当前版本策略 |
|---|---|---|
| `main` | 保存用户确认的正式版本基线 | 本轮按明确授权同步 `0.2.10`；不直接打包 |
| `develop` | 集成已确认变更，构建并发布正式版 | 本轮正式版本 `0.2.10`，按保护规则完成集成后打包 |
| `feature` | 开发、修复和试用验证 | 保留已发布的 `0.2.9` 预发布；新功能仍按预发布渠道验证 |

## 测试版与合并

1. 在 `feature` 完成修改、相关测试和 VSIX 检查，再分发测试版。
2. 若为测试版创建 GitHub Release，标记为 **Pre-release**，不设为 **Latest**。上传 Marketplace 时，VSIX 清单也必须包含预发布标记；只给 GitHub Release 加标签不够。
3. 测试版验证稳定后，等待用户明确通知，才能将对应变更合入 `develop`。测试通过、发布测试版或时间经过均不构成合并授权。
4. 按用户确认范围准备集成 PR，说明版本、行为和发布规则变更；用户明确委托执行本轮合并时，按仓库正常要求完成合并，不改变保护设置。未经明确授权不合入 `main`。
5. 合并后从实际 `develop` 提交打包正式版，核对安装包、版本、来源提交与许可证，再上传商店，并按用户授权同步 `main`。准备作为正式版的版本号不先作为 feature 预发布上传。

2026-10-24，用户确认 0.2.9 试用通过，明确要求同步合并到 `develop/main` 并正式发布。本轮据此集成已验收内容与 0.2.10 发布元数据，结束原先 main 保持 0.1.0 的冻结安排。受保护分支条件尚未满足时保持 PR 待处理；不改规则、不强推、不绕过必要审批。本轮授权不构成以后自动合并或自动发布的许可。

## 打包与上架渠道

| 当前分支 | 打包命令 | 允许的渠道 |
|---|---|---|
| `feature` | `npm run package -- --pre-release` | GitHub Pre-release、Marketplace Pre-release |
| `develop` | `npm run package` | 经确认的正式发布 |
| `main`、其他分支、分离 HEAD | 拒绝直接打包 | 不从这些位置生成安装包 |

打包脚本读取实际 Git 分支，拒绝 feature 正式包和 main 直接打包；普通构建与测试不受限制。Marketplace 本身不识别 Git 分支，上传前仍须核对包的来源；不要绕过脚本直接使用其他打包入口。合并遵循用户明确授权与服务端保护要求，不能把本地准备完成写成远端已合并。

预发布和正式版使用不同版本号，不用同一版本号跨渠道覆盖。0.2.9 已从 feature 按预发布渠道分发；本轮正式版使用独立的 `0.2.10`。`0.2.4` 至 `0.2.8` 为此前本地验证记录。保留既有安装包和 tag，不移动或覆盖；源码归档从 v0.2.10 起按已提交属性排除 output 产物，并核对实际归档。

市场图标须为 PNG/JPEG，大小不超过 1024 KB。打包脚本在创建输出前检查图标路径、格式与大小；预览包检查通过不等于 Marketplace 已上架。

## 版本一致性

每次打包核对 `package.json`、`package-lock.json` 中本项目的版本、打包输出文件名、VSIX 清单和 Git tag。它们必须指向同一版本及对应提交。

例如，`0.1.1` 测试版使用 tag `v0.1.1`，安装包命名为 `fpga-workbench-0.1.1-win32-x64.vsix`。创建 tag 前完成该版本的验证；不移动已有版本 tag，也不以不同内容覆盖同一版本的已分发安装包。

`feature` 的临时版本号不自动决定 `develop` 或 `main` 的下一版本。合并前需核对目标分支的版本计划，保留测试结果及必要的变更说明，等待用户确认本次合并范围。
