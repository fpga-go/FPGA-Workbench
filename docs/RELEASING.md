# 分支与版本维护规范

每次变更都由用户决定是否合并。未经用户明确通知，不自动合并分支、不推进正式发布，也不新增自动发布流程。

## 三条分支的职责

| 分支 | 职责 | 当前版本策略 |
|---|---|---|
| `main` | 保留正式版本基线 | 当前保持 `0.1.0`，冻结新发布；未经用户通知不合入变更、不升级版本 |
| `develop` | 集成用户确认稳定的变更，发布商店正式版 | 已发布 `0.2.3`；后续正式版在用户网页合并后另定版本 |
| `feature` | 开发、修复和试用验证 | 当前 `0.2.9`；GitHub 和 Marketplace 均只能发布 Pre-release |

## 测试版与合并

1. 在 `feature` 完成修改、相关测试和 VSIX 检查，再分发测试版。
2. 若为测试版创建 GitHub Release，标记为 **Pre-release**，不设为 **Latest**。上传 Marketplace 时，VSIX 清单也必须包含预发布标记；只给 GitHub Release 加标签不够。
3. 测试版验证稳定后，等待用户明确通知，才能将对应变更合入 `develop`。测试通过、发布测试版或时间经过均不构成合并授权。
4. 为集成准备 `feature` → `develop` PR，说明版本、行为和发布规则变更。最终由仓库所有者在 GitHub 网页确认合并。未经明确通知不合入 `main`。
5. 合并后从 `develop` 打包正式版，核对实际安装包、版本、来源提交与许可证，再上传商店。准备作为正式版的版本号不先作为 feature 预发布上传。

## 打包与上架渠道

| 当前分支 | 打包命令 | 允许的渠道 |
|---|---|---|
| `feature` | `npm run package -- --pre-release` | GitHub Pre-release、Marketplace Pre-release |
| `develop` | `npm run package` | 经确认的正式发布 |
| `main`、其他分支、分离 HEAD | 拒绝发布打包 | 无 |

打包脚本读取实际 Git 分支，拒绝 feature 正式包和 main 发布包；普通构建与测试不受限制。Marketplace 本身不识别 Git 分支，上传前仍须核对包的来源；不要绕过脚本直接使用其他打包入口。授权与保护规则不能区分同一账号通过网页或 API 的操作，自动化不得代替所有者执行合并。

预发布和正式版使用不同版本号，不用同一版本号跨渠道覆盖。2026-10-23 本次发布前已核实商店正式版为 `0.2.3`、预发布版为 `0.2.2`；当前 `0.2.9` 从 feature 按预发布渠道分发。`0.2.4` 至 `0.2.8` 为本地验证记录。保留既有安装包和 tag，不移动或覆盖；后续正式版须在用户网页合并到 develop 后另定版本。

市场图标须为 PNG/JPEG，大小不超过 1024 KB。打包脚本在创建输出前检查图标路径、格式与大小；预览包检查通过不等于 Marketplace 已上架。

## 版本一致性

每次打包核对 `package.json`、`package-lock.json` 中本项目的版本、打包输出文件名、VSIX 清单和 Git tag。它们必须指向同一版本及对应提交。

例如，`0.1.1` 测试版使用 tag `v0.1.1`，安装包命名为 `fpga-workbench-0.1.1-win32-x64.vsix`。创建 tag 前完成该版本的验证；不移动已有版本 tag，也不以不同内容覆盖同一版本的已分发安装包。

`feature` 的临时版本号不自动决定 `develop` 或 `main` 的下一版本。合并前需核对目标分支的版本计划，保留测试结果及必要的变更说明，等待用户确认本次合并范围。
