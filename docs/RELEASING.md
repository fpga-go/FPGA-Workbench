# 分支与版本维护规范

维护者批准每次合并和发布。
批准只适用于指定版本和分支。
验收通过不等于批准合并。
验收通过不等于批准发布。
不得自动合并或发布后续版本。

## 三条分支的职责

| 分支 | 职责 | 当前版本策略 |
|---|---|---|
| `main` | 保存正式版本基线 | 同步目标为 `0.2.10`。不直接打包。 |
| `develop` | 正式构建与发布 | 正式版本为 `0.2.10`。集成后打包。 |
| `feature` | 开发和试用验证 | 保留 `0.2.9` 预发布。新功能继续试用。 |

## 预发布

1. 在 `feature` 完成修改。
2. 执行与修改内容对应的测试。
3. 检查 VSIX。
4. 分发预发布版。

GitHub 测试版必须标记为 **Pre-release**。
不要将测试版标记为 **Latest**。
VSIX 清单也必须包含预发布标记。
GitHub 标记不能替代 VSIX 清单。

## 合并与正式发布

维护者批准合并范围后，准备集成 PR。
PR 说明版本、行为和发布规则的修改。
服务端保护条件未满足时，保持 PR 待处理。
不得改变保护设置。
不得强推。
不得绕过必要审批。

未获批准，不得合入 `main`。
0.2.10 的批准范围包含 `develop` 和 `main`。
`main` 不再固定在 0.1.0。
后续版本必须单独批准。

1. 合并已验收内容。
2. 从 `develop` 的实际提交打包。
3. 检查安装包版本。
4. 检查来源提交。
5. 检查许可证。
6. 上传商店。
7. 同步 `main` 正式基线。

准备正式发布的版本不能先用于预发布。

## 打包与上架渠道

| 当前分支 | 打包命令 | 允许的渠道 |
|---|---|---|
| `feature` | `npm run package -- --pre-release` | GitHub 和 Marketplace Pre-release |
| `develop` | `npm run package` | 经批准的正式发布 |
| `main`、其他分支、分离 HEAD | 拒绝直接打包 | 不在这些位置打包 |

打包脚本检查实际 Git 分支。
`feature` 不得打包正式版。
`main` 不得直接打包。
未知分支不得打包。
分离 HEAD 不得打包。
普通构建和测试不受此限制。

Marketplace 不识别 Git 分支。
上传前检查安装包来源。
不得绕过打包脚本。
本地准备完成不代表远端已合并。

预发布和正式版使用不同版本号。
不得将预发布版本号用于正式版。
0.2.9 来自 `feature` 预发布。
0.2.10 使用独立的正式版本号。
0.2.4 至 0.2.8 为历史本地验证记录。

保留既有安装包。
不得移动旧 tag。
不得覆盖旧 tag。
不得覆盖已分发的安装包。

从 `v0.2.10` 起，源码归档排除 output 产物。
归档规则必须提交到 `.gitattributes`。
下载实际源码归档后，检查归档内容。

图标使用 PNG 或 JPEG。
图标不得超过 1024 KB。
脚本在创建输出前检查图标。
检查范围包括路径、格式和大小。
打包通过不代表 Marketplace 已上架。

## 版本一致性

每次打包检查以下版本信息：

- `package.json` 中的项目版本。
- `package-lock.json` 中的项目版本。
- 打包输出文件名。
- VSIX 清单。
- Git tag。

这些信息必须指向同一版本和对应提交。
0.1.1 预发布使用 tag `v0.1.1`。
对应安装包如下：

```text
fpga-workbench-0.1.1-win32-x64.vsix
```

创建 tag 前，完成该版本的验证。
不得用不同内容覆盖已分发安装包。
`feature` 临时版本不决定 `develop/main` 的下一版本。
合并前检查目标分支的版本计划。
保留测试结果。
保留修改说明。
维护者批准合并范围后再合并。
